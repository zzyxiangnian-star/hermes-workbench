## 背景
电商工作台的“经营”页：看各店流量、转化、投放花费和 ROI，ROI 低于阈值或花费超了马上提醒，每天早上出一份日报。第一期数据还是从客户导出的报表来。

## 数据模型（新增，字段名照用）
- `daily_metrics`：id、date、shop_id、visitors、orders、sales_amount、refund_amount（可空）、updated_at；唯一键 (date, shop_id)。转化率、客单价由接口计算，不存。
- `ad_spend`：id、date、shop_id、tool（万相台 / 京准通 / 多多推广 / 巨量千川 / 其他）、campaign（计划名）、spend、gmv、clicks（可空）、impressions（可空）、updated_at；唯一键 (date, shop_id, tool, campaign)。ROI = gmv / spend，接口计算。
- `ad_rules`：同 `rules` 的结构，kind 有三种（见下）。
- `alerts`：id、kind、level、shop_id、campaign（可空）、date、message、status（open / resolved / ignored）、found_at、resolved_at、note。去重和自动转已处理的逻辑照 C01 的 issues。
- 引入 Alembic 管理表结构变化（C01 的表做成第一个迁移），以后迁 PostgreSQL 也靠它。

## 导入
- `POST /api/import/metrics`、`POST /api/import/ad-spend`：和商品导入同样的方式（xlsx/csv、自动识别中文列名、可传 mapping、坏行记录不中断、记进 `import_runs`，`import_runs` 加一个 kind 字段区分）。
- 样表：`samples/metrics-tmall.xlsx`（30 天 × 1 店）、`samples/ad-spend-tmall.xlsx`（30 天 × 4 个计划），故意放几天 ROI 很低、某天花费突增，再放 2 行坏数据。

## 投放规则（ad_rules）
1. `roi_below`：某计划当天 ROI < `min_roi`（默认 2）且花费 ≥ `min_spend`（默认 200）→ warn
2. `spend_over_cap`：某计划当天花费 > `daily_cap`（按计划名配置的字典，没配置的不检查）→ must
3. `spend_spike`：某计划当天花费 > 前 7 天平均的 `spike_pct`%（默认 150%）→ warn
导入后自动跑；`POST /api/ad-rules/run` 手动跑。消息写中文，说清计划、日期、数字，例如“万相台·双11预热 11-04 ROI 1.3，低于 2”。

## 接口（/api 下）
- `GET /overview?date=&shop_id=&brand=` → 当天和前一天对比：访客、订单、销售额、转化率、客单价、投放花费、投放 GMV、ROI，每项带环比；外加当天 open 的 alerts 数。
- `GET /overview/trend?days=30&shop_id=&metric=` → 折线用的日序列。
- `GET /ad-spend?date_from=&date_to=&shop_id=&tool=` → 按计划汇总的列表（花费、GMV、ROI、是否有提醒）。
- `GET /alerts?status=&level=&shop_id=`、`PATCH /alerts/{id}`、`GET /alerts/summary`。
- `GET /ad-rules`、`PATCH /ad-rules/{id}`。
- `GET /reports/daily?date=` → 日报内容（JSON + 一段排好版的 Markdown 文本）：总览数字、环比、异常店铺、open 的商品问题数和投放提醒前 5 条。
- `POST /reports/daily/send?date=` → 发到飞书或企业微信群机器人。地址从环境变量 `WB_FEISHU_WEBHOOK` / `WB_WECOM_WEBHOOK` 读，都没配置时返回 400 “没有配置推送地址”；带 `dry_run=true` 时只返回将要发送的内容不发。

## 定时任务
用 APScheduler 跑在服务进程里：每天 `WB_DAILY_AT`（默认 08:30）先跑商品规则和投放规则，再生成日报；配置了推送地址才发送。启动参数 `WB_SCHEDULER=off` 可关掉（测试里关掉）。
